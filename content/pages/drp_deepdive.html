The DRP AI Assistant

The hub ships an interactive DRP Assistant — a chat agent over the registry API that helps researchers discover, describe, clone and mature Digital Research Products from natural language. It streams responses (SSE), surfaces the tool calls it makes (each answer can be traced back to the originating API call), keeps per-user chat history, and can be extended with a configurable terminal proxy for repository and execution actions. Admins configure the model endpoint and the assistant's behavior in settings; the p4n instance is pre-production (BETA) and not a citable corpus.

WCEDMVO — a computed maturity model

Registry methodology that separates an evolving product from the evidence backing its current assessment. A product keeps one identity while its component references are attached, replaced or detached; maturity is then computed per record revision from explicit, inspectable gates — a level plus the exact unmet criteria, not a black-box score.

  • W · Workflowmanifest, step order, parameters, entry command
  • C · Coderepository with release or commit reference
  • E · Environmentdependency specification, container image reference
  • D · Datainput references, versions, checksums, access conditions
  • M · Metadatadescription, creators, citation, license
  • V · Validation & provenancescoped checks, outcomes, recorded runs
  • O · Outputstables, figures, reference results, tolerances

The L0–L4 maturity ladder

Gates are cumulative: failing L2 (e.g. removing the environment image) drops the product to L1, and all higher gates fall with it. A level describes local policy conformance — it is a navigation aid, not a certificate of scientific validity or full FAIR compliance.

L0RegisteredA product record exists.
L1DocumentedDescription ≥ 80 characters; at least one of git_url, workflow_file or entry_command present.
L2Citable & specifiedLicense, citation-file URL and environment image present; a release tag or commit other than HEAD recorded.
L3Execution-evidencedWorkflow or command, validation scope, a passed validation-run record, and provenance URL or last-run binding.
L4Publication-orientedDOI and archive URL present, public visibility, human review recorded.

FAIR in DRP-Hub — and where it stops

The ladder and the FAIR principles answer different questions: FAIR concerns properties of data and metadata (persistent identity, semantic interoperability, stewardship); the ladder orders selected local obligations. Each FAIR principle maps to a supporting mechanism — DOI/archive (F1, L4), description + citation + license (F2, L1–L2), HTTPS API and artifact links (A1/A1.1/A1.2), separate registry record for metadata retention (A2), structured metadata with possible RO-Crate export (I1), component links (I3) and license + provenance + workflow fields (R1.1–R1.3) — while the remaining evidence obligations stay explicit gaps. In short: DRP-Hub makes FAIR trackable field by field; it does not by itself certify FAIR compliance.
